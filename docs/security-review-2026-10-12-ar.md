# مراجعة الأمان والاستقرار لمشروع OpenCode Bridge

**تاريخ المراجعة:** 12 أكتوبر 2026  
**المدخل:** الأرشيف `opencode-bridge-main_2.zip`، إصدار المصدر `2.0.0`  
**حالة التسليم:** تغييرات مُطبقة على نسخة عمل مستقلة؛ ليست إصدارًا إنتاجيًا مُعتمدًا ولا دليلًا على صلاحية جميع المسارات التشغيلية. بقي رقم الإصدار كما هو لتجنّب الإعلان عن إصدار لم يُنشر.

## 1. نطاق المراجعة

فُحصت بنية المشروع ومصادر Python وملفات الإعداد والنشر والاختبارات الحالية، مع فحص مركز لمسارات تنزيل الملفات (SSRF)، استخراج ZIP، تشغيل العمليات في Sandbox، عزل Workspaces، النشر الذري، قراءة الأسرار واتصالات OpenCode المحلية. تمت مطابقة توجهات الحماية مع توثيق OpenCode لخادم HTTP ووثائق GitHub Actions الأمنية كما كانت متاحة حتى تاريخ المراجعة.

هذه **ليست** شهادة تدقيق أمني شامل، ولا اختبار اختراق للشبكة، ولا إثباتًا على توافق كل استدعاء من استدعاءات OpenCode مع نسخة الخادم المثبتة لديك.

## 2. الإصلاحات المنفذة

| الملف | التعديل | الأثر |
|---|---|---|
| `bridge/services/download_service.py` | فحص كل قفزة Redirect قبل الاتصال، تعطيل بروكسي البيئة، رفض بيانات الدخول داخل URL والمنافذ غير الصالحة ومحارف التحكم، أسماء تنزيل عشوائية غير تصادمية، تسلسل العمليات عبر قفل محلي، كتابة سجل JSON ذريًا مع fsync، تنظيف ملفات الكتابة الفاشلة | تقوية حماية SSRF وسلامة الفهارس والحصص |

| `bridge/infrastructure/security/secrets.py` | التحقق من أسماء ملفات الاعتماد ورفض المسارات الرمزية الخارجة عن مجلد الاعتمادات | منع قراءة مسار غير متوقع إذا مُرِّر اسم غير موثوق |

| `start.sh` | توجيه فحص صحة OpenCode المحلي دون بروكسي | منع توجيه الاتصال المحلي عبر بروكسي النظام |
| `.github/workflows/quality-gate.yml` | تفعيل فحص `scripts/quality.sh` داخل CI مع Ruff مضبوط على `0.17.0` | تحويل بوابة جودة كانت موجودة إلى فحص مطلوب لبناء الإصدار |
| `tests/test_2026_security_regressions.py` | 14 اختبار انحدار ضد المدخلات العدائية وحالات التزامن وفشل التخزين | اكتشاف تكرار عيوب الأمان مستقبلًا |

## 3. نتائج التحقق الفعلية

- نجحت **14/14** حالة الاختبار الجديدة على Python **3.13.5**.
- نجحت الاختبارات المختارة المرتبطة بمسارات التنزيل وOpenCode والأرشيف وWorkspace وSandbox والنشر والاعتمادات.
- نجح `compileall` وفحص JSON وYAML والصياغة الخاصة بشيفرات Shell.
- في التشغيل العام لمجموعة الاختبار بعد إضافة 14 اختبارًا: **465 اختبارًا، 30 خطأ من النوع البيئي، دون حالات FAIL**. كانت أخطاء 30 موجودة في خط الأساس أيضًا بسبب غياب `aiosqlite` و`python-telegram-bot` والاختبار الذي يطالب بوجود الإصدارات المثبتة نفسها. 435 اختبارًا لم تسجل خطأً في ذلك التشغيل.
- لم يُنفَّذ Ruff محليًا لعدم توافره، لكن بوابة Ruff أصبحت مفروضة في GitHub Actions؛ نجاحها على الخادم البعيد **غير مؤكد بعد**.
- لم يُنفَّذ اختبار كامل لخادم Telegram/OpenCode حقيقي، ولا اختبار load/soak مطوّل، ولا استعادة SQLite حقيقية.

## 4. مخاطر تحتاج عملًا قبل النشر النهائي

### مرتفعة الأولوية (P0)

1. **DNS rebinding/TOCTOU**: فحص DNS منفصل عن إنشاء اتصال TCP؛ رغم منع Redirect الداخلي مسبقًا، قد يتغير عنوان DNS بين الفحص والاتصال. فرض شبكة خروج (egress ACL/firewall) تحظر العناوين الخاصة/الداخلية، أو نقل الاتصال إلى resolver/dialer يثبت عنوان IP بعد التحقق، ضروري لتأمين تنزيل الروابط على خادم ذي صلاحيات واسعة.
2. **صلاحيات OpenCode**: إعداد `opencode.json` يحتوي على `bash: {"*":"allow"}` و`external_directory: "allow"` مع حظر بعض الأنماط فقط. القائمة السوداء للأوامر لا تشكل عزلًا متينًا، ويمكن التحايل عليها بصيغ أو أدوات أخرى. يلزم فصل وكيل التنفيذ إلى مستخدم/حاوية بصلاحيات دنيا ووضع سياسة سماح محددة أو طلب موافقة للأوامر الحساسة.
3. **التحقق الفعلي من الإنتاج**: يلزم تثبيت التبعيات المحددة في البيئة المعتمدة وتشغيل جميع الاختبارات وSmoke/E2E قبل الترقية، مع لقطة/نسخة احتياطية قابلة للاستعادة.

### متوسطة الأولوية (P1)

4. **فهرس التنزيلات JSON**: القفل الحالي يحمي نسخ الخدمة ضمن العملية الواحدة فقط، ولا يمنع تضارب عمليات متعددة أو أعطالًا بين ترقية الملف والفهرس؛ الأفضل تحويله إلى SQLite ضمن معاملات ACID وحجوزات حصص فعلية مع اختبارات crash-recovery.
5. **النسخ الاحتياطي المشفر**: عند تفعيل `encrypt` يُكتب ملف `.enc` إضافي، لكن تظل النسخة غير المشفرة على القرص. هذا **لا** يحقق تشفير البيانات وقت السكون؛ ينبغي كتابة نسخة مشفرة فقط أو إدارة مفتاح تشفير وخيارات تخزين واضحة بعد التحقق من سلوك الاستعادة.
6. **سلسلة التوريد**: `requirements.lock` يثبت الإصدارات دون hashes إلزامية؛ وتستخدم GitHub Actions مرجع الوسم `@v7` بدل SHA كامل ثابت. تحسين ذلك باستخدام hash locking وربط Actions بمعرّفات commit موثوقة، وتجهيز SBOM/فحص ثغرات.
7. **التغطية متعددة الإصدارات**: CI يستهدف Python 3.14 فقط؛ ينبغي الاختبار في مصفوفة 3.12 و3.13 و3.14، مع اختبار توافق OpenCode عبر عقد OpenAPI من الخادم الفعلي.
8. **الاستقرار والأداء**: تنفيذ اختبارات طويلة الأمد مع تداخل إعادة التشغيل، انقطاع الشبكة، تأخير API، امتلاء القرص، وإلغاء مهام شغالة تحت حمل متزايد.

## 5. التوصيات التشغيلية

1. انشر أولًا إلى **بيئة staging** مماثلة لخادم الإنتاج، ولا تستبدل `.env` أو قاعدة البيانات أو مجلدات المهام الفعلية أثناء التجربة.
2. افحص نتيجة بوابة GitHub Actions الجديدة؛ إذا فشل Ruff، أصلح المخالفات التي يُبلغ عنها قبل الموافقة على النشر.
3. بعد تشغيل `python -m pip install -r requirements.lock -c constraints.txt` في **بيئة بناء/اختبار** مخصصة، نفّذ `python -m pip check` و`python -m unittest discover -s tests -p 'test_*.py' -v`؛ لا تتجاوز الفحوص الفاشلة.
4. فعّل قيود الوصول إلى الشبكات الداخلية على مستوى نظام التشغيل أو الحاوية، وراجع هوية مستخدم خدمة OpenCode والصلاحيات على مجلدات المشاريع.
5. اختبر فعليًا تنزيل ملف صغير، إعادة توجيه محظورة، Telegram handlers، حفظ واستعادة SQLite، التراجع عن النشر، إيقاف المهمة وإعادة تشغيل الخدمة.
