# مواصفات نظام التحكم عبر Telegram

**الحالة:** مسودة تصميم للمراجعة البشرية قبل إعداد خطة التنفيذ.

**المستودع:** `Alaa91H/opencode-bridge`

**المرجع الأساسي:** فرع `main` عند `8822f190858cf122bdf898f1ad0bdb1e99cac61d` (2026-10-08).

## الهدف

توسيع OpenCode Bridge الحالي ليصبح واجهة تشغيل يومية آمنة من Telegram لإدارة مهام الوكيل، موارد الخادم وخدماته، وجدولة العمل، وعمليات GitHub المصرح بها. يبقى SSH وسيلة طوارئ مستقلة. يعتمد التصميم على الطبقات والخدمات والطابور وقاعدة SQLite الحالية، ويتجنب إضافة وسيط رسائل أو قاعدة بيانات أو خدمة عامة جديدة دون حاجة مثبتة.

## الخيارات المعمارية

1. **تغيير شامل واحد:** بناء واجهة وكل التكاملات والنشر في PR واحد. وقت أولي أقل، لكنه يصعّب عزل الأعطال ويزيد أثر أي خطأ على خادم محدود الموارد.
2. **توسيع مرحلي للمعمارية الحالية (الموصى به):** إعادة استخدام `PanelRouter` وطبقات `services` وSQLite وموصل GitHub، وإضافة محولات صغيرة مع Issue وPR واختبارات لكل مرحلة. يسمح بإيقاف التوسع عند فشل بوابة دون فقد الميزات المستقرة.
3. **خدمة تحكم مستقلة:** واجهة/API وقاعدة/عمال منفصلون. تقدم فصلًا أكبر، لكنها تستهلك موارد وتضيف سطحًا عامًا وتشغيلًا وصيانة غير مبررة حاليًا.

## التصميم المقترح

### الوحدات ومسار البيانات

- **واجهة Telegram:** توسيع القوائم المتداخلة الموجودة إلى لوحة Dashboard، المهام، الخادم، المستودعات، الفروع وPRs وIssues، Actions، الإصدارات، الوكلاء، الجدولة، السجلات، التنبيهات، الأمان والنسخ الاحتياطي. تعرض الصفحات حالة المصدر وتوقيتها، وتستخدم صفحات البحث والتقسيم والتحديث، وتوفر العربية والإنجليزية إذا كانت الرسائل قابلة للتوطين. لا تعرض نسبة تقدم إلا إذا وصلتها قيمة فعلية من المصدر، ولا يظهر زر قبل ربطه واختبار أثره.
- **الهوية والصلاحيات:** بوابة موحدة لكل أمر وزر. التشغيل الإداري في المحادثة الخاصة فقط. أدوار owner/admin/operator/reader قابلة للتهيئة؛ لا يُضاف أي مستخدم مميز من Telegram. يبدأ الإعداد بصاحب الحساب الموثق حاليًا، ولا تُمنح أدوار إضافية افتراضيًا.
- **موافقات العمليات الحساسة:** موافقة صريحة منفصلة لحذف مستودع، force push، تعديل صلاحية/سر، إعادة تشغيل الخادم أو تغيير بيانات إنتاجية غير قابلة للتراجع. تكون الموافقة لمستخدم مخول، ولمورد وفعل محددين، قصيرة الصلاحية، أحادية الاستخدام، ومسجلة في التدقيق. النشر الاعتيادي الناجح بالبوابات أدناه لا يحتاج موافقة بشرية لكل إصدار وفق توجيه المستخدم.
- **سجل المهام:** مصدر الحقيقة لتغيير حالة مهمة هو مخزنها الأصلي. يعرض محول موحد مهام SQLite، GitHub Actions وOpenCode عند توافر بياناتها دون دمج دلالات الحالات المختلفة. تحفظ العمليات المحلية والأحداث/الأخطاء في الجداول الموجودة أو migrations لازمة؛ ويحتفظ كل مصدر بمعرفه ورابطه ووقت البداية والمدة والمرحلة والخطوة التالية وآخر نشاط وسجل الأخطاء. تعرض واجهة المهمة الاسم والوصف والمستودع والنوع والأولوية والحالة والتقدم الفعلي. توفر start/pause/resume/cancel/retry وتعديل أولوية queued فقط عندما يدعمها المصدر وسياسة الحالة؛ لا يجوز أن تعيد الواجهة حالة متقادمة إلى التنفيذ أو تنفذ مرتين.
- **طابور الأتمتة:** ينفذ Issues الخاصة بالمستودع الذي اختاره المستخدم بالتسلسل المحدد، وبترتيب رقم Issue عند عدم وجود ترتيب صريح، مع حفظ checkpoint/الفرع/PR/آخر فحص. لا يبدأ Issue تابعًا قبل نجاح متطلباته. لا يفقد العمل عند إعادة التشغيل أو quota pause. الحد الأقصى المطلق 3 أعمال متزامنة، وتخفض سياسة الموارد الحد إلى 0–2 عند الضغط؛ لا تُلغى المهام الجارية لمجرد ارتفاع الضغط.
- **GitHub:** موصل API بصلاحيات credential الفعلية، ونطاق المستودع المسموح، وسياسة لكل عملية. يعرض المستودعات المصرح بها مع البحث والحالة؛ الملفات والفروقات وسجل commits ومقارنة refs؛ الفروع وPRs ومراجعاتها وتعليقاتها وchecks؛ Issues وlabels وmilestones وassignees؛ workflows وruns وjobs/logs/artifacts؛ وtags/releases/changelog. تنفذ عمليات الإنشاء/التعديل المعتادة التي يسمح بها token، مثل issue وPR وفرع وworkflow_dispatch أو cancel/rerun؛ إغلاق issue بعد قبولها، والدمج التلقائي بعد البوابات، وإدارة الإصدار وفق سياسة الإصدار. يبدأ الاستعراض بالقراءة، ثم الكتابة الضرورية عبر API/Git الآمن. لا يتجاوز إنشاء PR أو الدمج checks أو rulesets. لا force push ولا حذف مستودع ولا تغيير صلاحية بلا موافقة صريحة. لا يخزن البوت أسرار الوصول في سجلات أو يرسلها إلى Telegram.
- **Webhooks:** استقبال الحدث اختياري فقط عند توفر endpoint HTTPS متاح وآمن؛ يُفرض HMAC signature والتحقق من replay/idempotency ومصدر المستودع. الجرد الحالي لم يكشف endpoint تطبيق HTTPS عام. حتى توفيره، يستخدم الموصل polling محدودًا مع ETag/backoff؛ لا يفتح منفذًا عامًا أو يعرض OpenCode للإنترنت لمجرد تفعيل webhooks.
- **إدارة الخادم:** لوحة تعرض قياسات قابلة للقراءة مع عمر العينة، بما فيها المتاح فعلًا من CPU/RAM/Swap/disk/load/uptime/network/processes/حرارة واستخدام log/cache وقاعدة البيانات والاتصال بـGitHub وTelegram. تُظهر «غير مدعوم» للحساس غير المتاح. عمليات systemd مقيدة بوحدات معلومة ومصفوفة start/stop/restart/logs/health المسموحة مع صلاحيات وتأكيدات؛ وتعرض Docker فقط بعد اكتشافه. تنظيف الملفات محصور بمسارات التطبيق المؤقتة وبفحوص عمر/ملكية/مسارات واضحة؛ لا shell عام ولا أوامر حرة. تحديثات النظام لا تدخل في أوامر عامة عشوائية.
- **الأتمتة والتنبيهات والنسخ:** تعريفات الجدولة الحالية تبقى دائمة. تضاف outbox/dedup للتنبيهات مع مستويات لكل مشروع وتصفية التكرار. تستخدم النسخ SQLite online API وmanifest/checksum/integrity، وسياسة احتفاظ، وتشفير وتخزين خارجي عند توافر وجهة موثوقة؛ يختبر مسار الاستعادة آليًا ولا تنفذ استعادة مدمرة دون موافقة.
- **الوكلاء:** يعرض النظام الجلسات/الوكلاء التي تكشفها واجهة OpenCode فعلًا. pause/resume/cancel أو التكلفة لا تظهر إلا إذا كانت واجهة المزود توفرها. لا يُدّعى وجود قياس تكلفة أو نسبة إكمال غير متاحة.

### سير التطوير والاختبار والنشر المستمر

1. لكل Issue فرع قصير العمر من `main` وPR يربط معايير القبول والتغييرات ودليلها. المنفذ يكمل issue واحدة تلو الأخرى ويحتفظ بحالة قابلة للاستئناف.
2. GitHub Actions يبني/يجهز artifacts ويشغل الاختبارات؛ لا يجري compile أو tests أو dependency installation على production. تتضمن البوابات unit/integration/contract/Telegram mock E2E/security/syntax/code-quality والاختبارات المناسبة لتغيير المصدر.
3. يراجع آليًا اكتمال المعايير ومخرجات الاختبارات وفروقات الصلاحيات، ويفشل مغلقًا عند secrets أو فحوص ناقصة. يدمج GitHub PR تلقائيًا بعد تحقق البوابات المطلوبة والحماية؛ لا تُعطل حماية الفرع للحصول على الدمج.
4. يفصل workflow بين إصدارات stable وRC؛ لا يحاول Release إنشاء إصدار stable من قيمة RC. كل نشر يشير إلى SHA وartifact ثابتين مع checksum، لا إلى checkout متغير.
5. بعد دمج main واجتياز البوابات، ينشر GitHub Actions تلقائيًا إلى الإنتاج دون موافقة متكررة، على مراحل قابلة للرصد: تحقق من artifact/النسخة والنسخة الاحتياطية، تفعيل release ذري، readiness/smoke حقيقي، ثم تثبيت الإصدار. يستخدم runner مستضافًا في GitHub للإنشاء والاختبارات؛ لا يشغّل runner بناءً على خادم 951 MiB.
6. فشل health/smoke أو migration يعيد symlink/الإصدار السابق تلقائيًا، يحفظ السجلات والنسخة، ويوقف تتابع النشر ليعالج السبب. لا يكرر نشرًا متقلبًا بلا حد. أخطاء quota تؤجل الطلب حتى وقت التجديد المدعوم؛ وأخطاء المصادقة أو فقد credential أو موافقة destructive تصبح حالة تنتظر إصلاحًا أو موافقة مناسبة.
7. لا يشترط soak لمدة 24–72 ساعة لكل تغيير. تفرض سياسة مخاطر soak أطول فقط لتغيير قاعدة بيانات/ترحيل غير عكوس، حدود أمنية مركزية، دورة طابور أو نشر واسعة الأثر، أو تغيير يرفع مخاطر الأداء والاستقرار وفق evidence. بقية التغييرات تعتمد smoke/rollback وقياسًا قصيرًا محددًا.
8. يخطر Telegram بالبدء، الفشل، التراجع والاكتمال مع رابط run/PR، دون رسائل متكررة للحالة نفسها. يحتفظ SSH بصفته مسار استعادة طارئ منفصلًا.

### مراحل المشروع ومعايير قبولها

1. **الأساس والحوكمة:** تسوية حالة T50–T54 مع الواقع، تثبيت هذا التدقيق، إنشاء Issues بالاعتماديات، وتعريف بوابات main وخرائط صلاحيات الإنتاج. القبول: لا تعارض في مصدر حالة التنفيذ، وكل Issue لها معايير ومالك/ترتيب واضح.
2. **المصادقة والتدقيق:** private-only، فصل الأدوار، موافقات مستهدفة قصيرة العمر، حماية callbacks المكررة، وتحسين نزاهة سجل التدقيق. القبول: اختبارات رفض للمستخدم/المجموعة/الدور والزر القديم/المعاد، وأثر تدقيق لكل عملية إدارة.
3. **مركز المهام والخادم:** عرض حالات وتاريخ حقيقيين والتحكم المدعوم، عرض صحي لمصادر النظام، وأفعال systemd الآمنة. القبول: اختبارات SQLite وTelegram callback وresource fail-closed، وعدم عرض progress وهمي أو تنفيذ مرتين.
4. **GitHub وCI/CD:** قائمة المستودعات وفق الصلاحيات، قراءة الملفات/الفروع/PR/Issues/Actions، ثم الكتابة المسموح بها وwebhooks المحمية، auto-merge بعد الحماية، ونشر artifact ذري قابل للتراجع. لا يظهر وجود staging الآن؛ لذلك تختبر GitHub Actions خطة التفعيل والتراجع في بيئة معزولة، وتتحقق أول عملية إنتاج آلية من health/smoke مع rollback تلقائي. القبول: sandbox API mocks، فشل مع credentials/permissions ناقصة، التحقق من signature/replay، وإثبات نجاح/فشل/rollback على SHA معلوم دون بناء على الخادم.
5. **الجدولة والتنبيهات والنسخ والوكلاء:** دمج أحداثها في لوحة واحدة مع سجلات وتعافي. القبول: restart/retry/fault tests، dedupe notifications، checksum واستعادة fixture، وتأكيد أن أي تحكم Agent معروض مدعوم من API.
6. **التحقق التشغيلي:** اختبارات تزامن وموارد وضغط ومراجعة أمنية ورصد بعد النشر وتحديث دليل التشغيل. القبول: كل بوابة مرتبطة بالـSHA، وrollback مجرب، وتقارير `NOT TESTED` صريحة لأي إثبات لا توفره بيئة GitHub. اختبارات التكامل المحاكية وE2E تُشغّل آليًا على كل تغيير ذي صلة؛ حمل الأداء القصير يطابق مخاطر التغيير، ولا يستهلك الخادم الإنتاجي الضعيف لأغراض التحميل.

## ضوابط ثابتة

- لا بناء أو اختبار أو تثبيت اعتمادات على production؛ GitHub Actions هو مصدر التحقق.
- لا تشغيل shell مفتوح من Telegram، ولا أسرار في الرسائل أو logs.
- لا يتجاوز التزامن 3، وتسمح سياسة الموارد بإيقاف بدء أعمال إضافية عند الضغط.
- لا حذف لمستودع/فرع غير تابع للمهمة أو تجاوز حماية/موافقة أمنية.
- لا استخدام متطلب quota أو تقدم أو حالة أو capability غير مؤكدة.
- لا يغلق Issue قبل الدمج وفحوص SHA النهائي ونجاح معايير قبوله.
