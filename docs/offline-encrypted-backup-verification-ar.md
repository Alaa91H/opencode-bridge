# التحقق من النسخ الاحتياطية واستعادتها — T04

هذه عملية فحص خارجية في جهاز استعادة منفصل، لا تلمس قاعدة بيانات الإنتاج ولا تتطلب حفظ مفتاح فك التشفير على الخادم.

## السياسة

- تُحفظ بصمة SHA-256 لكل نسخة SQLite عادية ويُتحقق من البصمة وسلامة SQLite قبل احتسابها نقطة استعادة.
- يستعمل إنشاء النسخة تدفقًا على كتل بدل تحميل قاعدة البيانات كاملة في ذاكرة الخادم.
- تبقى النسخ القديمة غير الموقعة ظاهرة، ولكن لا تُحتسب لاستيفاء العدد الأدنى قبل تأكيد سلامتها يدويًا.
- النسخ ذات الأسرار تُشفّر بـ age بالمفتاح العام، ويبقى المفتاح الخاص خارج خادم الإنتاج.

## اختبار نسخة age على جهاز منفصل

انسخ النسخة المشفرة وملف معلوماتها ذي اللاحقة .age.json إلى جهاز موثوق عليه age ومفتاح فك التشفير، ثم:

```bash
python scripts/verify-encrypted-backup.py /recovery/backup-20261013T010000-deadbeef.age /recovery/age-identity.txt
```

يرفض الفاحص اختلاف البصمة، والروابط الرمزية، والأرشيفات التالفة أو ذات المسارات غير المعروفة أو المكررة، وغياب ملف sessions.db أو فساده. يُنشئ مساحة مؤقتة خاصة، يفك التشفير فيها دون استخراج الأسرار، ويفحص SQLite ثم يتخلص من الملفات المؤقتة. يُطبع تقرير JSON بلا أي أسرار.

يجب ألا يُحفظ مفتاح age الخاص على خادم الإنتاج. اجعل صلاحيات الملف 0600 في Linux.

## المتبقي

هذه اختبارات برمجية ولا تثبت نجاح فك تشفير نسخة واقعية بالمفتاح الفعلي أو استعادة الحاوية والخدمات في بيئة staging. يبقى إثبات استعادة قاعدة حقيقية، وسلامة حالات WAL والمهام، وقياس وقت الاستعادة RTO ومدة فقد البيانات RPO شروطًا قبل التفعيل التلقائي الإنتاجي.
