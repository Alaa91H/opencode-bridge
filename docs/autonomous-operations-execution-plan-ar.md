# OpenCode Bridge — خطة الإدارة الذاتية والتطوير الآمن

**تاريخ الأساس:** 2026-10-12  
**الفرع المرجعي:** `main` عند `a9097cb1bfd3352688659fd1f940b2a5a427bf52`  
**هدف التنفيذ:** إدارة OpenCode Bridge وOpenCode وخادم Ubuntu بصورة تلقائية مستقلة، مع قابلية الاستعادة والتدقيق والتحكم من Telegram.

> **سجل الأدلة الأحدث:** [تقدم المراحل T01–T18 بتاريخ 2026-10-13](autonomous-operations-evidence-2026-10-13-ar.md)، مع الفصل بين نجاح CI ومتطلبات قبول الإنتاج.

> هذه خطة تنفيذ، وليست تقريرًا بأن جميع البنود اكتملت. أي ميزة تتطلب صلاحيات إنتاجية لا تُفعّل قبل اجتياز اختبارات CI وstaging وإثبات التراجع. لا نعد بانعدام الحاجة لأي تدخل بشري في حالات العتاد أو فقدان الوصول أو الكوارث.

## مبادئ غير قابلة للتجاوز

1. ممنوع البناء والاختبار الثقيل على خادم الإنتاج؛ تصل إليه artifacts موثوقة من CI فقط.
2. تبقى `.env` و`runtime/` و`sessions.db` ومساحات العمل مستقلة عن كود الإصدار.
3. كل تغيير إنتاجي له هوية commit وإصدار وmanifest ونتيجة تحقق قابلة للمراجعة.
4. لا تحديث متزامن لعنصرين قد يتنافسان على APT أو إيقاف الخدمات أو قاعدة البيانات.
5. لا أسرار صريحة في ردود Telegram أو ملفات السجلات؛ إرسال النسخ المتضمنة مفاتيح يكون مشفرًا بمفتاح عام مُدار خارج الخادم.
6. كل إجراء root ينفذه مكوّن محدود الصلاحيات بأوامر ثابتة، وليس نص أوامر حرًا صادرًا عن LLM.
7. تُرفض التحديثات المتراجعة أو غير المتوافقة أو مجهولة المصدر، وتُحفظ آخر نسخة سليمة وقابلية العودة.
8. التوقف الآمن وطلب تدخل استثنائي أفضل من تكرار عطل أو إفساد حالة لا يمكن استردادها.

## آلة حالات التحديث المطلوبة

`DISCOVERED → VERIFIED → STAGED → BACKED_UP → QUIESCED → ACTIVATED → HEALTH_CHECKING → SOAKING → COMMITTED`

كل انتقال مُسجّل في SQLite مع `operation_id` و`source_sha` و`artifact_digest` و`previous_release` و`attempt_count` و`started_at`. كل تشغيل متكرر للعملية ذاتها يجب أن يكون idempotent. أي فشل قبل COMMITTED يقود إلى `ROLLING_BACK` ثم `ROLLED_BACK` إن نجحت الاستعادة، أو `NEEDS_ATTENTION` مع إيقاف محاولات النشر الجديدة.

- التحقق قبل التفعيل: checksum + provenance + CI success لنفس commit + metadata/version + توافق مخطط SQLite + الموارد.
- النسخ: SQLite Online Backup ثم `integrity_check` ثم إثبات توفر المساحة ونجاح التشفير.
- النقل: رابط `current` يُغيّر ذريًا فقط بعد نجاح preflight ولا يتم تغيير checkout التشغيل الحي مباشرة.
- الصحة: systemd + health API + task queue + اتصال Telegram/OpenCode + smoke request غير مؤثر.
- التراجع: يستعيد النسخة السابقة *وحالة البيانات المتوافقة*؛ المهاجرات غير القابلة للعكس ممنوعة ضمن ترقية تلقائية.
- بعد الفشل المتكرر: circuit breaker إلى أن تتغير نسخة artifact أو تحل المشكلة.

## أوضاع التشغيل

| الوضع | السلوك |
|---|---|
| `off` | لا تحديثات تلقائية؛ أدوات الفحص والنسخ الاحتياطي متاحة حسب إعداداتها |
| `notify` | يتحقق ويبلغ، دون تفعيل |
| `auto-safe` | يطبق تحديثات موثوقة ومتوافقة وقابلة للاستعادة بدون تأكيد متكرر |
| `maintenance-window` | مثل `auto-safe`، لكن يطبّق التغييرات أثناء نافذة محددة |
| `emergency-stop` | يمنع كل تغيير جديد ويحافظ على القراءات/التشخيص |

مفاتيح مستقلة: `bridge_update`, `opencode_update`, `os_security_update`, `auto_repair`, `backup`, `auto_reboot`. لا تغيّر إعدادات قديمة أو تعيد تفعيلها خلسة أثناء الترحيل. القيمة الافتراضية الآمنة لأية صلاحية جديدة مؤثرة في الإنتاج هي `off` إلى أن تنجح اختبارات الترحيل.

## واجهة الإدارة المطلوبة

`Server → Overview | Health | Services | Resources | Updates | Backups | Credentials | Security | History`.

كل عملية مؤثرة تعرض: المصدر، الإصدارات القديمة والجديدة، زمن العملية، نتائج preflight، زر التراجع عند توفره، آخر نسخة سليمة، وسبب التوقف. واجهات المفاتيح تعرض الأسماء والبصمات والحالة فقط. تبديل الاعتماد يتم باختبار صلاحية الجديد قبل إزالة القديم.

## اختبارات القبول

- سباق عمليتي نشر، غياب شبكة GitHub، archive تالف، tag متحرك، حصة قرص منتهية، backup فاسد.
- انقطاع التشغيل في كل مرحلة من الانتقالات، اختبار إعادة الدخول idempotent بعد restart.
- مهاجرة قاعدة بيانات فاشلة، rollback مع بيانات مهام قيد التنفيذ وSQLite WAL.
- توقف Telegram أثناء تحديث OpenCode، وتعطيل نظام التحديث والعودة بعد تعطيله.
- رفض تحديث النظام عند عمليات APT أخرى، وعدم تنفيذ reboot إذا كانت هناك مهام حساسة.
- تعذر استعادة الإصدار السابق: `NEEDS_ATTENTION` بلا حلقات لا نهائية.
- جميع handlers بصلاحيات مختلفة، محادثة عامة/خاصة، وهوية مجهولة.
- تحمّل 24–72 ساعة مع قياس الأداء ومعدل الفشل والحصص واستهلاك RAM.

## مؤشرات قبول أولية

- صفر فقد غير مقصود للمهام أو الأسرار في اختبارات الفشل.
- صفر ترقيات إنتاجية دون artifact موثوق واجتياز preflight.
- كل نتيجة تحديث مسجلة ويمكن تتبع مصدرها؛ لا يفترض النجاح من exit code وحده.
- هدف الاستعادة للحوادث القابلة للتعافي: خلال 15 دقيقة (يُقاس في staging).
- `auto-safe` لا يوسّع صلاحيات الوكيل ولا ينفذ تغييرات بنيوية غير قابلة للاستعادة.
