# خارطة تطوير الإدارة الذاتية لـ OpenCode Bridge

**تاريخ الإعداد:** 2026-10-12  
**خط الأساس:** الفرع `main` عند `a9097cb1bfd3352688659fd1f940b2a5a427bf52` والإصدار `3.2.0`.  
**الحالة:** خطة تنفيذ مرحلية وليست إعلانًا عن جاهزية الإنتاج.

## الهدف

تطوير Bridge إلى منصة تشغيل ذاتي لإدارة وكيل OpenCode وTelegram والمستودعات والخادم، مع تحديثات موثوقة يمكن تشغيلها **بصورة اختيارية** دون تدخل بشري في الحالة الطبيعية. لا يعني الوضع التلقائي تجاوز اختبارات السلامة، أو إعادة التشغيل الخطرة، أو تغيير الصلاحيات والأسرار دون تحكم صريح.

## مبادئ ملزمة

1. لا بناء أو تثبيت تبعيات التطبيقات على خادم الإنتاج؛ تبنى الحزمة في CI وتُنشر كأثر غير قابل للتغيير وموقّع/موثق.
2. القواعد الأمنية fail-closed؛ لا تُمكّن ميزات تنفيذ الأوامر المميزة بمجرد نجاح المصادقة في Telegram.
3. لا تفقد أي مهمة أو ملف اعتماد أو قاعدة بيانات عند التحديث أو إعادة تشغيل الخدمات.
4. أي تغيير تلقائي يسجل: هوية المصدر، سبب التغيير، البصمة، الاختبارات، التفعيل، قياسات الصحة، نتيجة الرجوع.
5. لا إعادة تشغيل قسرية للنظام أثناء مهام نشطة؛ التحديثات التي تتطلب reboot تبقى معلّقة حتى تُجتاز شروط السلامة.
6. لا تعرض التوكنات في Telegram أو السجلات؛ إرسال نسخ تحتوي مفاتيح يجب أن يكون مشفرًا بمفتاح عام خارج الخادم.
7. لا تعِد باستعادة ذاتية من فشل القرص الفيزيائي أو فقدان اتصال الخادم بالشبكة دون بنية مراقبة/استعادة مستقلة.

## مراحل التنفيذ (12 حزمة متتابعة)

### A01 — خط أساس قابل للقياس (P0)
- توثيق نسخة الإنتاج الفعلية وSHA وملف الخدمة ووقت آخر نشر؛ مقارنة checkout وrelease الحالي.
- بوابة اختبارات Python متعددة الإصدارات، lint، shell syntax، فحص التبعيات والمنافذ، تقارير قابلة للأرشفة.
- اختبارات منع تداخل مهمتين ومقارنة نتائج CI مع hash الأثر الذي سيُنشر.
- **قبول:** يمكن معرفة الإصدار الفعلي العامل والتأكد من إمكانية إعادة إنتاج حزمته، ولا توجد نتائج اختبارات مطلوبة غير معلومة.

### A02 — إصلاح مسار النشر والرجوع (P0)
- توحيد `scripts/deploy.sh` و`maintenance/activate_artifact.py` و`self_update.py` حول آثار CI الموثقة.
- نشر ذري إلى مجلد إصدارات ثابت، مع مساحات تشغيل وبيانات مشتركة منفصلة، وتبديل الرابط الفعّال بعد الاختبارات.
- قفل توزيعي/محلي لكل نشر، تحقق من manifest/checksum/commit/tag، وإقلاع تجريبي ضمن حدود زمنية.
- تراجع عن الكود وقاعدة البيانات بعد فشل تفعيل أو ترحيل، مع إثبات استعادة الخدمة وإعادة المهام.
- **قبول:** اختبارات حقن خطأ قبل التفعيل وبعده، رفض الأرشيفات الضارة، استعادة نسخة معروفة جيدة دون فقد بيانات.
- **منفذ على الفرع الأول:** إصلاح تحويل SHA إلى tag مطابق في rollback، واختبارات عقد الأداة.

### A03 — محرك تحديثات تلقائي موحّد (P0)
- إنشاء `UpdateCoordinator` بحالات: discovered → verified → staged → drained → activated → observed → healthy / rolled_back / quarantined.
- مصادر مستقلة: Bridge، OpenCode، حزم النظام؛ لكل مصدر سياسة وقناة إصدار ونافذة صيانة ودرجة خطورة.
- حظر إعادة نشر الإصدار الفاشل مع السماح بإصدار أحدث مُتحقق منه، وإيقاف سلسلة المحاولات المتكررة.
- تحديثات Bridge عبر نتائج CI/Release فقط، لا عبر `git pull` مباشرة في الإنتاج.
- تحديث OpenCode بإصدار محدد مع حفظ مسار ثنائي سابق وفحص تكامل API وإعادة النسخة السابقة عند الإخفاق.
- تحديث حزم Ubuntu عبر آلية آمنة قابلة للتعقب؛ تأجيل التغييرات التي تتطلب تدخلًا أو إعادة تشغيل غير آمنة.
- **قبول:** فشل GitHub أو DNS أو امتلاء القرص لا يبدّل الإصدار العامل؛ التحديثات المستحيلة لا تتكرر بلا حد.
- **منفذ على الفرع الأول:** حجر إصدار Bridge الفاشل عن التحديث اليومي.

### A04 — مفتاح «الوضع التلقائي» وسياسات قابلة للتحكم (P0)
- مفتاح رئيسي اختياري: `OFF / GUARDED / AUTONOMOUS`، القيمة الافتراضية الجديدة `GUARDED` بعد ترحيل الإعدادات القائمة دون تعديل نية المالك.
- مفاتيح مستقلة لكل من Bridge وOpenCode وتحديثات أمن النظام والنسخ الاحتياطي والتنظيف والإصلاح الذاتي.
- حدود دقيقة للموارد ومهلة الاختبار وعدد الإعادات والحد الأقصى للتوقف ونوافذ الصيانة.
- المستوى AUTONOMOUS يطبق فقط العمليات المحددة مسبقًا والمسموح بها، ولا يتجاوز الصلاحيات أو يُجري تحديثًا تخريبيًا.
- **قبول:** كل مفتاح في Telegram يغيّر سلوك مهمة حقيقية، ويستمر عبر restart دون تناقض بين الواجهة والجدولة.

### A05 — إدارة الخادم من Telegram (P1)
- لوحة خدمة/مورد موحدة: CPU، RAM، ZRAM، swap، disk، I/O، PSI، الشبكة، uptime، خدمات systemd.
- فحص خدمات Bridge/OpenCode، إعادة تشغيل آمنة، سجل الأحداث، إصدار الأداة، عدد المهام، ضغط الذاكرة.
- «تحقق الآن» منفصل لكل مكوّن و«حدّث الآن» مع تقرير تدفقي محدود/محجوب الأسرار.
- زر إلغاء الصيانة، تعطيل الوضع التلقائي، عرض الحجر، وآخر نسخة سليمة، وتشخيص الحوادث.
- حارس إعادة التشغيل: يرفض reboot عندما توجد مهمة غير محفوظة أو استعادة غير مؤكدة.
- **قبول:** كل إجراء موثق بصلاحية ووصف واضح وتقرير نتيجة، ولا تنفذ أوامر Shell نصية حرة بصلاحيات root.

### A06 — الصلاحيات وعزل الوكيل (P0)
- تفعيل سياسة `owner/admin/operator/reader` بصورة fail-closed على مستوى جميع الأوامر وcallbacks.
- فصل وكيل التطوير عن خدمات الإدارة المميزة باستخدام مستخدم/حاوية ذات صلاحيات دنيا.
- حظر وصول الوكيل الافتراضي إلى `.env` والأسرار ومقبس Docker والمسارات الداخلية والشبكة الداخلية.
- حماية تنزيلات HTTP من DNS rebinding/SSRF على طبقة الاتصال والشبكة.
- **قبول:** اختبارات تجاوز الصلاحيات، تحوير callbacks، symlink traversal، session hijack، وقراءة الأسرار.

### A07 — مركز موحد للمفاتيح والاعتمادات (P1)
- توحيد جرد GitHub/Telegram/OpenCode/AI providers مع الاسم والنطاق والحالة والصلاحية وآخر استخدام.
- إضافة/تعديل/تعطيل/تبديل/حذف، كشف انتهاء الصلاحية والتحقق من المفتاح الجديد قبل التفعيل.
- منع العرض الخام للأسرار، تسجيل عمليات التغيير وحماية النسخ أثناء التدوير.
- **قبول:** تدوير مفتاح لا يقطع الخدمة إذا فشل الجديد؛ لا يسجل أي سر، ولا يمكن للقارئ عرض/تعديل المفاتيح.

### A08 — نسخ احتياطي واستعادة موثوقان (P0)
- لقطات SQLite متسقة مع التحقق `integrity_check` وWAL، ومُعرّفات التوافق ومخطط ترحيل.
- نسخ مشفرة فقط عند اختيار «بالمفاتيح»، بمفتاح عام خارجي؛ عدم إبقاء نسخة plaintext ثانوية.
- سياسة احتفاظ مختلفة للبيانات والإصدارات ومفاتيح الخدمة؛ عدم حذف آخر نسختين صالحتي استعادة.
- اختبار استعادة تلقائي دوري على نسخة مستقلة، وربط RPO/RTO بالتقارير.
- **قبول:** استعادة كاملة في بيئة اختبار من نسخة حديثة، مع إعادة مهام مؤجلة دون ازدواج.

### A09 — نظام تشخيص وإصلاح ذاتي (P1)
- كشف توقف Telegram/OpenCode، تدهور الذاكرة، امتلاء التخزين، فشل DNS، تعليق الطوابير وانخفاض القدرة.
- قواعد إصلاح محددة: retry/backoff/circuit breaker ثم restart لمكوّن واحد ثم rollback ثم quarantine.
- تقليل عدد العمال آليًا تحت الضغط دون قتل مهمة جارية؛ سجل حدث مع سبب محدد وتقييم النتيجة.
- **قبول:** تمرين أعطال يشمل انقطاع شبكة وقاعدة بيانات مقفلة وفشل API وانفجار تحميل، بلا حلقات إعادة تشغيل.

### A10 — تطوير قدرات وكيل OpenCode (P2)
- سجل قدرات وأدوات وموفري نماذج قابل للاكتشاف، سياسات تفضيل تكلفة/سرعة/جودة واختبار توافق API.
- مهام طويلة قابلة للاستئناف وcheckpoint، سياق ملخص متين، مهام مترابطة DAG بشرط التحكم بالتزامن.
- عزل مستودعات متعددة وإدارة اختلاف الأدوات والأذونات دون منح صلاحيات النظام.
- **قبول:** استئناف المهمة بعد إعادة تشغيل Bridge دون تنفيذ الأوامر ذات الأثر مرتين.

### A11 — تنزيلات ومرايا وتخزين منظم (P2)
- اكتشاف مرايا مجانية دون حساب، اختبار قدرات HTTPS والحجم وانتهاء الرابط والشروط قبل إظهارها.
- اختيار مزودين متعددين وتحقق بصمة الملفات بعد النقل وتحويل الفشل لمصدر آخر.
- تنظيف 24 ساعة ثم الإزالة عند أول 00:00 UTC لاحق للاستحقاق، مع حجز حصة القرص.
- **قبول:** عدم رفع الأسرار إلى المرايا العامة؛ لا استخدام لخدمة تتطلب تسجيلًا باعتبارها مجانية عامة.

### A12 — إصدار نهائي ومراقبة طويلة الأمد (P1)
- تشغيل مصفوفة CI وE2E وfault injection والـ soak، ثم canary، ثم نشر تدريجي.
- مراقبة مؤشرات نجاح المهام، الإخفاق، p95، زمن تعافي الخدمة، التكلفة، واستهلاك الموارد.
- تدقيق أمني وإصدار موقّع مع سجل تغيير ودليل rollback واختبار استعادة بيانات.
- **قبول:** اجتياز جميع معايير الإنتاج، وغياب أعطال P0 مفتوحة، وتأكيد صحة الإصدار الجاري على الخادم الحقيقي.

## أسلوب التشغيل المستهدف

```text
Telegram Control Plane
     │   سياسات وصلاحيات
     ▼
Autopilot / UpdateCoordinator ─────► Audit & Observability
     │
     ├── Bridge stable release ────► Verified CI artifact ─► Staging ─► Atomic switch
     ├── OpenCode pinned version ──► Compatibility / health ────────► Controlled restart
     ├── OS security updates ──────► APT policy / reboot guard
     └── Backup / restore tests ───► Encrypted off-host retention
                                      │
                                 Failed health?
                                      │
                               Rollback + quarantine
```

## معيار «دون تدخل»

يمكن للنظام إنجاز تحديثات روتينية تلقائيًا بعد تفعيل المالك للسياسات واختبار مسار العودة. أما اختراق أمني، أو فقدان الشبكة نهائيًا، أو تلف القرص، أو تحديث غير متوافق دون إصدار سابق صالح، فهي حالات توقف آمن مع إنذار، ولا يُدَّعى حلها برمجيًا دون بنية استعادة مناسبة.

## التتبع

استخدم قضية GitHub واحدة لكل حزمة، مع قائمة قبول واختبارات وروابط PR. لا تُغلق قضية بالنص وحده؛ يلزم دليل CI ناجح وتحقق staging، ثم دليل نشر إن كانت تغيّر الإنتاج.
