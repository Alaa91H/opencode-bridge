# v3.40.0 — One destructive host operation at a time (2026-10-17)

## Finding

The control panel's update buttons were fire-and-forget. `_running_updates` in
`control_ui.py` only keeps task references alive; nothing prevented a second
press from starting a second host operation. Every comparable service already
had a lock (`admin_backups.lock`, `host_credentials.lock`, `provider_keys`,
`download_service._transfer_lock`) — the most destructive path was the only one
without.

Consequences of a double press:

- two `apt-get upgrade` runs contend on the dpkg lock and can leave a
  half-upgraded system;
- two `self_update.py --apply` transient units deploy the same release at once;
- two `opencode upgrade` runs restart the agent service independently.

## Change

- `bridge/services/host_operations.py`: `HostOperationGuard` plus the
  process-wide `HOST_OPERATIONS` instance, with Arabic labels per operation kind.
- `server_admin.update_now()` validates the kind, then delegates the whole
  operation to the guard. A concurrent request is refused immediately with an
  explanation naming the running operation — never queued behind a long apt run.
- The guard always releases, so a failed or timed-out update cannot block the
  owner's next attempt.

## Tests

`tests/test_host_operation_guard.py`: refusal while busy, serial ordering,
release after an exception, label coverage, and `update_now` delegation. No test
runs a host command.

## Still to wire (next cycle)

`HostController.reboot` / `restart_service` / `cleanup_now` should consult the
same guard, because rebooting in the middle of an upgrade is the worst case. The
guard already exposes `busy` and `current` for that; the controller file could
not be edited in this cycle (the workspace file-edit tool was failing), so it
was left whole rather than half-applied.

## Upgrade

No deps, no migrations. Source release only.
