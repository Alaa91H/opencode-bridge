# OpenCode Bridge v1.7.0

## Highlights

- Turned Telegram photos, videos, audio items and arbitrary documents into instruction-bound queued agent tasks.
- Added persistent staging for files sent before their instruction, including multi-file batches and Telegram media groups.
- Added server-side fallback processing for PDF, audio, video and other binary formats that OpenCode does not expose directly to the model.
- Added task-local selection of a zero-cost OpenCode Zen model with explicit image capability for visual media work.
- Hardened attachment integrity, retention, prompt-injection boundaries and temporary-file isolation.

## Telegram Attachment Workflow

- A media/file message with a caption becomes one queued task immediately.
- A media/file message without a caption is stored as a pending batch; the next ordinary text message in the same chat becomes its instruction.
- Multiple pending uploads are combined into one task.
- Telegram media groups are debounced and submitted as one task instead of one task per item.
- Pending batches survive bridge restarts, expire automatically, and can be removed manually with `/discard`.

## Server-Side Media Processing

- UTF-8 text and model-visible image formats are attached directly to OpenCode.
- PDF, audio, video and other binary files remain available through validated local server paths.
- The agent is instructed to use only already-installed, read-only processing tools such as `ffprobe`/`ffmpeg`, `pdftotext`/`pdftoppm`, `file`, `strings`, and archive-listing tools when appropriate.
- Intermediate conversions are confined to a per-task scratch directory and are removed automatically.
- Only final files written to the managed output directory are returned to Telegram.
- If the required server-side parser/codec is unavailable, the agent reports the limitation instead of installing packages or fabricating analysis.

## Model Capability Routing

- Visual media tasks can temporarily prefer an active zero-cost OpenCode Zen model whose live catalog metadata explicitly advertises image input.
- The capability-specific choice is task-local and does not permanently replace the user's general model selection.
- Paid, unpriced, unavailable and text-only candidates cannot be promoted by this media-specific selector.

## Security & Reliability

- Every downloaded attachment is recorded with a SHA-256 digest.
- Before execution the bridge revalidates managed path containment, symlink rejection, exact size and content digest.
- Attachment contents are explicitly treated as untrusted data, not agent instructions.
- Incoming scripts, binaries and macros are never executed merely because they were attached.
- Per-file, per-task count and aggregate-byte limits prevent unbounded intake.
- Telegram confirmation failures no longer discard a successfully queued or staged attachment task.
- Incoming files are removed after non-recurring task execution reaches its terminal path; expired pending files and task scratch data are also cleaned safely.

## Configuration

New or expanded settings in `.env.example`:

- `TELEGRAM_ATTACHMENT_MAX_BYTES`
- `TELEGRAM_ATTACHMENT_MAX_COUNT`
- `TELEGRAM_ATTACHMENT_MAX_TOTAL_BYTES`
- `TELEGRAM_ATTACHMENT_PENDING_SECONDS`
- `TELEGRAM_MEDIA_GROUP_DEBOUNCE_SECONDS`

## Verification

- Added deterministic tests for SHA-256 tamper detection, aggregate limits, prompt-injection boundaries and scratch cleanup.
- Added restart-persistence, merge, expiry and rollback tests for pending attachment batches.
- Added tests for OpenCode-visible attachment format routing.
- Added tests proving media model selection requires explicit image capability and remains restricted to zero-cost OpenCode Zen candidates.
- GitHub Actions remains the source of truth for Python syntax, unit tests, OpenCode configuration, semantic versioning and release publication.
