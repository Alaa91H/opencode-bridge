# v3.42.0 — One schedule promotion per interval (2026-10-17)

## Finding

Every worker called `store.promote_due()` on every poll. That method opens
`BEGIN IMMEDIATE`, runs several statements and commits — a write transaction on
the single shared SQLite connection, under the queue lock. With three workers
and a five-second poll, an idle bridge paid up to three identical no-op write
transactions every five seconds, forever, all serialized behind the same lock
that `claim_next`, heartbeats and status updates need. Redundant maintenance that
grows with the pool size is worse than none.

## Change

- `TaskServiceV3._promote_if_due()` runs promotion at most once per poll
  interval for the whole pool, behind a lock plus a monotonic timestamp so
  concurrent workers cannot both promote.
- The interval is unchanged, so the worst-case delay for a due schedule is
  exactly what it was: one poll interval. The first tick after start promotes
  immediately.
- A failed promotion resets the timestamp so the next tick retries; the
  worker's existing error handling still logs and continues.

## Tests

`tests/test_promotion_coalescing.py`: concurrent workers promote once,
in-interval calls skipped, interval expiry, retry after failure, first tick,
pool promotes far less often than it polls, worker survives a failing store.

## Upgrade

No deps, no migrations. Source release only.
